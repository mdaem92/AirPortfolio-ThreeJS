# Performance improvement plan

Preserve the approved lighting, glass, shadows, vehicle effects and visual design. The original findings below are a source/asset audit. Step 1 has a local production baseline in [performance/baseline-report-2026-11-02.md](performance/baseline-report-2026-11-02.md), covering desktop and a narrow desktop viewport. Step 2 now has an uncommitted camera controller and arrival-gated welcome-board flips; review notes are in [performance/camera-navigation-review.md](performance/camera-navigation-review.md). Physical-phone timing is still outstanding. Terminal/tower lighting work and the optional measurement tooling remain uncommitted.

## Findings

- Camera focus currently runs through five useFrame subscriptions. Active routes use fixed per-frame interpolation factors (0.05–0.1), call lookAt before moving the camera, and continue adjusting the camera after arrival. Drei OrbitControls also updates that camera every frame at priority -1 with a different target. These are strong candidates for uneven transitions and control contention; confirm with traces.
- Skills starts ten model animation actions when selected and mounts its content after a fixed 2,000 ms delay. Projects waits 1,800 ms, then mounts a carousel and its images. These timers are unrelated to camera arrival and can put UI/layout/image work into the transition tail.
- The Draco-compressed scene is 3,220,400 bytes, but contains approximately 1,556,389 unique POSITION-accessor vertex records across 82 meshes, 31 materials and 20 animation clips. This is not the number of vertices actually drawn each frame. Radar: 674,828 vertex records / 337,594 triangles. Engine 2: 286,140 / 143,680. Engine 1: 286,136 / 143,680. Those three meshes account for about 80% of vertex records. Projects focuses on engine 2.
- There are only five embedded images, totaling approximately 428 KB; texture compression should not be assumed to be the main loading opportunity. Older About/welcome image data remains inside the GLB even though those screens now use HTML.
- The production JavaScript bundle is approximately 1.62 MB, 468 KB gzip. App and overlay modules are imported eagerly. Actual wire transfer, parse time, geometry decoding, GPU upload and shader preparation need separate measurement.
- Scene-ready currently follows component mounting, without explicit GPU warm-up. First encounters with materials, buffers or animation poses may therefore still hitch. Warm-up can also lengthen loading, so avoid blocking Start on unnecessary work.
- Contact-shadow opacity is zero in the approved preset, but its instanced mesh remains visible when shadows are enabled, so vehicle grounding matrices still update every frame. Terminal glass and steady ground-marker uniforms/colors are also updated every frame despite changing only through controls.
- Audio already loads after Start and independently of the scene. It is not a prerequisite for the initial ready state; inspect its first-click cost separately.

## Safe implementation order

1. **Capture a production baseline.** Use the built preview, not Vite development performance. Record cold and cached loading and first/repeated Main → Skills → Main → Projects navigation on desktop and a phone. Measure frame-time percentiles, worst frames/long tasks, draw calls, triangles, program count and load stages. Include the whole-render-frame cost when transmission, reflections and shadows use multiple passes. Keep the exact approved light settings and viewport fixed for comparisons.

   Local baseline captured; physical-phone follow-up remains. User clarified that returning from Skills/Projects to Main is the primary symptom. Prioritize those return paths in every subsequent comparison. The baseline records camera endpoint discrepancies, first-render preparation stalls, whole-frame render cost and return-board remount/flip work as a separate candidate.
2. **Give camera movement one owner.** Consolidate route motion into one transition controller. Interpolate position and viewing target with elapsed time/delta, retain the existing destinations and familiar pacing, and stop at a defined arrival tolerance. Suspend OrbitControls during automatic motion and synchronize its target/limits before returning control. Preserve update ordering before transformed HTML projection. Test rapid route changes, Escape, focus/free camera and all back buttons.
3. **Separate navigation from section preparation.** Prepare lightweight overlay content and the first project's images before arrival, keeping inactive content inert and hidden. Reveal when the camera arrives, replacing fixed delays. Profile the Skills animation startup and schedule its first poses/bindings to avoid a first-frame spike while preserving visible animation. Never postpone the camera itself behind a slow carousel mount or image decode.
4. **Improve the loading pipeline.** Render the boarding pass from a small entry chunk; split secondary project/carousel/overlay code, while explicitly preserving an early model request. Add staged loading feedback for transfer, model preparation and ready state. Warm critical shaders/textures with compileAsync/initTexture using final lighting, then prepare other views incrementally when idle. Compare total ready time and navigation hitches together: merely moving every stall into a longer loading screen is not a win. Check real hosting cache/compression headers; use versioned asset URLs before adopting long-lived immutable caching. Preserve the explicit Start audio gesture.
5. **Optimize geometry in isolated copies.** Begin with the radar, then both engines. Evaluate removing redundant geometry, sharing genuinely equivalent engine geometry, and carefully reducing excessive tessellation. Compare engine close-ups, radar silhouette/motion, UVs, normals, materials, animation bindings and shadow output. Only pursue LOD or model partitioning if measurements justify it. Consider removing obsolete embedded screen textures and unused geometry as separate changes. Retain the source asset for rollback.
6. **Remove invisible per-frame work.** Skip grounding/contact-shadow rendering when opacity is zero. Cache object references instead of repeated name searches, reuse temporary arrays and avoid unnecessary world-matrix updates for stationary vehicles. Preserve nearest-light behavior when configured limits are reduced. Move static glass/marker uniform updates to setting changes. Keep dynamic headlight and beacon updates intact. Make each change independently measurable.

## Validation and rollback

Use the same routes, lighting preset, device and viewport before/after each step. Target approximately 16.7 ms frame budgets on 60 Hz devices, with particular attention to transition spikes and first-use versus repeat visits; actual targets depend on baseline/device capacity. Record cold/cached time to visible boarding pass, usable Start and a smooth first destination. Compare visual captures at matching views and animation poses, especially glass, engine close-ups, lights and DOM screen alignment. Check loading errors, keyboard/back navigation, audio visibility behavior and rapid interrupted transitions.

Do not reduce light counts, change their look, lower DPR/shadow quality, replace transparent glass or add automatic quality degradation as the first response. Those would require a separate visual tradeoff decision. Preserve originals for asset experiments and keep changes small enough to revert individually. No commits, pushes or deployments are authorized by this planning request.
